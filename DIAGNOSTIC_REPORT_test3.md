## 8. Other interesting errors

- **`LIBVA_DRIVER_NAME=radeonsi` already in the shell env** (SteamOS sets this in `/etc/profile.d/libva.sh`). Causes SDL's own VAAPI probe to short-circuit:
  > `SDL Warn: Skipping VAAPI fallback driver names due to LIBVA_DRIVER_NAME`
  
  Not a bug per se — SDL is correctly respecting the explicit user setting — but it means SDL will not paper over the underlying libva failure by trying alternate drivers.

- **OpenSSL 3.3.0 ABI mismatch (non-fatal):**
  ```
  /tmp/.mount_VibemiLOLCgc/usr/bin/../lib/libcrypto.so.3:
      version `OPENSSL_3.3.0' not found (required by /lib/libssl.so.3)
  ```
  Bundled `libcrypto.so.3` is older than the OpenSSL 3.3.0 symbols required by the system's `libssl.so.3`. Qt's TLS plugin loader tries every path under `/lib`, `/usr/lib`, `/lib64`, `/usr/lib64` and they all fail. Qt eventually falls back to `QTlsBackendCertOnly` / its bundled OpenSSL backend and HTTPS works (the 401 from Vibepollo proves the TLS handshake reached the server). Worth tidying up in the build, but not the cause of either active regression.

- **HDR result on this LCD panel:** `SystemProperties: Final HDR support status: DISABLED`. PR #5 (HDR gate) is functioning correctly on this device — the Legion Go S Z2 LCD is correctly identified as non-HDR.

## 9. Root cause — VAAPI

Three independent facts collide:

1. **The `artemis` binary uses `DT_RUNPATH = $ORIGIN/../lib`.** At runtime this resolves under the AppImage FUSE mount (`/tmp/.mount_VibemiLOLCgc/usr/lib`), so the **bundled** `libva.so.2` is loaded, not the system's.

2. **Bundled libva is version 1.20.0** (from the `1.20.0` version string baked into the SO). Per libva's standard driver-loading logic, it tries to dlsym `__vaDriverInit_<major>_<minor>` starting from its own version and walking down — so it probes for `__vaDriverInit_1_20`, `__vaDriverInit_1_19`, ..., down to the historical floor (`__vaDriverInit_0_30` or similar). **It never tries anything higher than `1_20`.**

3. **System `radeonsi_drv_video.so` exports exactly one driver-init symbol:** `__vaDriverInit_1_22@@libgallium-25.3.0.so` (confirmed via `nm -D`). Mesa 25.3 was built against libva 1.22.0, which is what SteamOS 3.8.5 ships.

The intersection of (2) and (3) is empty — there is no init symbol both sides agree on. libva 1.20.0 emits `has no function __vaDriverInit_1_0` (its last fallback name) and `vaInitialize` returns `VA_STATUS_ERROR_UNKNOWN`. Hardware decode is dead.

**PR #4's hook (`01-libva-driver-paths.sh`) is doing exactly what the commit claims** — it correctly exports `LIBVA_DRIVERS_PATH=/usr/lib64/dri:/usr/lib/dri`. The hook is not broken. The PR's underlying *premise* is what's wrong: the commit message states "the AppImage bundles its own libva.so.2 but no /dri/ backend drivers, so libva can't load anything." Pointing the bundled libva at the system drivers cannot work when the bundled libva is older than the API the system drivers were compiled against.

### Recommended fix (in order of preference)

1. **Stop bundling libva.** It's a thin ABI shim over the actual driver in `/dri`. Every modern desktop Linux ships libva.so.2; on SteamOS, Ubuntu 22.04+, Fedora 38+, Arch — all have ≥ 1.22. Drop `libva.so.2`, `libva-x11.so.2`, `libva-drm.so.2` from the AppImage payload and let the system one resolve. This is what the linuxdeploy "exclude list" is for.

2. **Bundle libva ≥ 1.22.0** so it knows `__vaDriverInit_1_22`. This keeps the AppImage hermetic on older hosts.

3. **Quick hot-fix without rebuilding libva:** add a second apprun-hook (e.g. `02-system-libva-preference.sh`) that prepends the system libva directory to `LD_LIBRARY_PATH`. Because `artemis` uses `DT_RUNPATH` (not `DT_RPATH`), `LD_LIBRARY_PATH` takes precedence and the system libva (1.22) is loaded instead of the bundled 1.20. Sketch:

   ```bash
   for _d in /usr/lib64 /usr/lib/x86_64-linux-gnu /usr/lib; do
       if [ -e "$_d/libva.so.2" ]; then
           export LD_LIBRARY_PATH="$_d${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
           break
       fi
   done
   ```

   Caveat: this also surfaces other system libs ahead of bundled ones — needs targeted testing to make sure nothing else breaks (Qt, SDL2, ffmpeg are obvious risks). Option 1 is cleaner.
